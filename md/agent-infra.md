# Инфраструктура для агентов: как разводить и не разориться

Заметки к разделу «Дорога в 3 уровень» / слайду «Практики как единая система».

---

## 1. Как выстраивать агентов, чтобы не мешали и было экономически целесообразно

### Исходные требования (тянут в разные стороны)

1. Дать агенту **работающее приложение**, чтобы он быстро работал.
2. Чтобы каждый разработчик мог запускать **несколько агентов**.
3. Чтобы они **не мешали** друг другу.
4. **Не получить огромный счёт** за инфраструктуру.

Конфликт: быстрый старт ↔ дешевизна, много агентов ↔ изоляция, «не мешали» ↔ дублирование ресурсов, «не платить» ↔ хочется всё переиспользовать.

### Корень развязки

Разделить то, что **дорого поднимать**, от того, что **должно быть изолировано**. Это разные оси:

- **Шарить** дорогое и неизменяемое (код, зависимости, базовый образ).
- **Форкать** дёшево и изолированно изменяемое (рабочая копия, БД).
- Держать всё **эфемерным** под жёсткими квотами.

### Слой 1. Код — изоляция через git worktree, не через копию репо

- Каждой задаче-агенту — свой **git worktree** (или CoW-клон через `git clone --shared` / overlayfs), а не полный `git clone`.
- Отдельная рабочая директория и ветка при общей `.git`-базе → агенты не видят файлов друг друга, нет гонок на ФС, диск почти не растёт.
- Поверх — **lock на ветку/задачу**: агент берёт задачу из очереди, ставит claim, никто другой её не трогает. Это и есть техническая основа multi-agent coordination.
- Параллельность ограничивается на уровне «одна задача — один worktree — одна ветка».

### Слой 2. Окружение — главный рычаг по деньгам

- **Стейтлес-зависимости** (код, npm/composer install, билд) — **кешируем и шарим**. Прогретый базовый образ + слой зависимостей переиспользуется всеми. Поднятие агента = `worktree add` + overlay поверх готового образа = секунды.
- **Стейтфул-зависимости** (БД, очереди, внешние API) — **изолируем, но дёшево**. Тут ловушка «работающего приложения»: полноценный Postgres/Kafka/Redis на каждого агента = улетающий счёт. Варианты по возрастанию изоляции:
  - общий инстанс БД, **схема/база на агента** — дёшево, но риск помех при миграциях;
  - **template database** (`CREATE DATABASE ... TEMPLATE`) или **снапшот тома** (ZFS/btrfs CoW, Neon/branching-БД) — мгновенный форк «работающего» состояния, платим только за дельту;
  - **эфемерный контейнер с засидженной БД** под задачу — максимум изоляции.
- **Рекомендация: template/branch БД** — это и «работающее приложение сразу», и изоляция, и почти бесплатно.

### Слой 3. Жизненный цикл — эфемерность вместо «всегда горячо»

- Соблазн держать приложение горячим — главный источник счёта.
- Окружение **создаётся под задачу из прогретого образа и умирает после merge** (динамические окружения, Sandboxing).
- Быстрый старт — за счёт **тёплого пула** заранее собранных образов/снапшотов, а не постоянно работающих инстансов.
- **Scale-to-zero**: нет активных задач — нет потребления.

### Слой 4. Экономические предохранители (Resource & cost limits)

- Лимит **одновременных агентов на разработчика** (3–5) и глобально на команду.
- **Токен-бюджет** и **таймаут на run** (агент в цикле не должен жечь бесконечно).
- **TTL на окружение** — висящие sandbox убиваются автоматически.
- Метка владельца/задачи на каждом ресурсе → видно, кто сколько ест.

### Сводка: как закрываются 4 требования

| Хотелка | Решение |
|---|---|
| 1. Работающее приложение, быстрый старт | Прогретый образ + кеш зависимостей + снапшот/branch БД из готового состояния |
| 2. Несколько агентов на разработчика | git worktree на задачу + дешёвый форк stateful-зависимостей + квота на число агентов |
| 3. Не мешают друг другу | Изоляция файлов (worktree) + изоляция данных (схема/template/snapshot) + lock на задачу |
| 4. Не разориться | Шарим дорогое-стейтлес, форкаем дёшево-стейтфул, эфемерность + scale-to-zero + жёсткие лимиты |

**Одной фразой:** шарить дорогое и неизменяемое, форкать дёшево и изолированно изменяемое, держать всё эфемерным под жёсткими квотами.

## 2. Next.js: несколько инстансов в Kubernetes или железный сервер с N агентами?

Короткий ответ: **ни то, ни другое в чистом виде.** В вопросе смешаны две разные задачи:

1. Где живёт **compute агента** (билд, тесты, typecheck)?
2. Где и **когда** живёт **запущенное Next.js-приложение**?

### Главная ошибка

«Один агент = один постоянно работающий `next dev` в поде». Именно это умножает счёт на N и упирается в лимиты.

### Нужен ли вообще hot `next dev` на агента?

В ~80% задач агенту нужны **batch-операции**: `tsc --noEmit`, `eslint`, `next build`, unit-тесты. Это burst-CPU, не долгоживущий сервер. Живой инстанс нужен только для HTTP/e2e/визуальной проверки — и тогда его поднимают **на минуту и гасят**.

> Не держать N штук `next dev` горячими. Поднимать приложение **по требованию** из worktree, гасить после проверки. Это снимает ~70% проблемы ещё до выбора «куб vs железо».

### Специфика Next.js (кусается именно при многих инстансах)

- **inotify-вотчеры** (`next dev` + chokidar) — лимит ядра **на ноду**, общий для всех подов на узле. N dev-серверов выжирают `fs.inotify.max_user_watches`. Для неинтерактивных агентов — `next build && next start` (без вотчинга), а не `next dev`.
- Связывающий ресурс — **RAM**, не CPU. Считать по пику при компиляции (0.5–1.5 ГБ на инстанс).
- N одновременных холодных компиляций = thundering herd. Спасают **общий кеш `.next`** и стаггеринг.

### Железный сервер / большой reserved-VM, агенты как контейнеры (не обязательно K8s)

- ✅ Самый дешёвый core-hour (в 2–4 раза дешевле on-demand облака).
- ✅ **Общий page cache** ОС: node_modules, git-объекты, базовый образ читаются всеми из горячей RAM. Для bursty dev-нагрузки — огромный выигрыш, которого в изолированных подах нет.
- ✅ Мгновенный старт: нет шедулинга и pull образа.
- ❌ Слабее изоляция (noisy neighbor: чужой билд занял ядра; OOM задевает соседей).
- ❌ Общие лимиты ядра (inotify, порты, PID), ручной lifecycle, SPOF, плохо масштабируется за одну коробку.

### Pod-per-agent в Kubernetes

- ✅ Чистая изоляция (cgroups, лимиты на под), декларативный lifecycle, тривиальная уборка, bin-packing по нодам, scale-to-zero — «платформенный» уровень.
- ❌ Оверхед на под, **cold start** (шедулинг + pull) бьёт по быстрому старту без тёплого пула.
- ❌ Page cache **не** шарится между подами → теряется дешевизна переиспользования.
- ❌ Кластер сам по себе — сложность и деньги.
- ⚠️ inotify всё равно общий **на ноду** — поды от этого лимита не спасают.

### Рекомендация

- **Сейчас (1–2 коробки, десятки агентов):** большой reserved-VM/железо + агенты в лёгких контейнерах (docker/podman), приложение по требованию, общие тёплые кеши. Изоляция на нужном уровне: worktree (файлы) + свой порт + своя schema/branch БД + cgroup-лимиты. Полноценный K8s избыточен.
- **Переезжать на K8s, когда:** не влезаете в одну ноду; нужен автоскейл/scale-to-zero под пик; уже есть кластер и команда эксплуатации; строите это как продукт-платформу. Тогда — pod-per-задача из прогретого образа, **обязательно тёплый пул подов**, неск. крупных нод + bin-pack, а не россыпь мелких подов.

**Развилка:** K8s, если он уже есть и вы упёрлись в одну машину; иначе одна жирная коробка с контейнерами почти всегда дешевле и быстрее на этом этапе.
